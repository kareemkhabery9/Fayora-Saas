# FayoraTravel SaaS — Transformation Plan

> حالة المستند: مسودة للمراجعة قبل أي تعديل في منطق النظام أو قاعدة البيانات.
>
> النطاق: التحويل المحلي لمشروع Fayora الحالي إلى منصة FayoraTravel SaaS متعددة
> المستأجرين. لا يترتب على هذا المستند أي تعامل مع مستودع بعيد أو GitHub.

## 1. قواعد المشروع غير القابلة للتفاوض

1. قاعدة بيانات واحدة مشتركة، وعزل كل بيانات الشركة عبر `CompanyId`.
2. العميل النهائي لا ينشئ حساباً ولا يسجل الدخول.
3. لا توجد بوابة دفع أو Webhook أو Refund أو Payout آلي؛ دفع الحجز يدوي عبر
   Mobile Wallet أو InstaPay وإيصال يرفعه العميل.
4. الشركة وحدها تدير محتواها وحجوزاتها وتقييماتها.
5. Super Admin يراقب المنصة ويدير حالة الشركة وسجل تجديدها اليدوي فقط؛ لا يغير
   محتوى الشركة ولا يؤكد أو يرفض حجزاً نيابةً عنها.
6. كل تغيير جوهري يسجل هنا قبل تنفيذ المرحلة التالية.

## 2. نقطة البداية التي تم فحصها

المشروع الحالي Backend مبني بـ .NET وClean Architecture وCQRS/EF Core، وطبقاته:

- `Fayora.Domain`
- `Fayora.Application`
- `Fayora.Infrastructure`
- `Fayora.Contracts`
- `Fayora.Api`

العناصر الصالحة لإعادة الاستخدام مبدئياً: JWT، التحقق بالبريد، OAuth Google/Facebook
(للشركات فقط بعد المراجعة)، Cloudinary، خدمة البريد، QR، بنية CQRS، EF Core والمigrations.

## 3. سجل قرارات التحويل المبدئي

| الجزء الحالي | القرار | سبب القرار / اتجاه التحويل |
| --- | --- | --- |
| `User` وJWT والتحقق بالبريد | تعديل | الحسابات ستنحصر في Company User وSuper Admin؛ تزال خصائص السائح غير اللازمة من المسار الجديد تدريجياً. |
| `TourCompany` | استبدال/إعادة تصميم | يتحول إلى `Company` SaaS: slug، theme، logo/cover، واتساب، وسائل دفع يدوية، حالة Trial/Active/Suspended. |
| `TravelPackage` و`PackageOccurrence` | تعديل | باقة تملكها شركة، بسعر بالغ/طفل، سياسة إلغاء محددة، ومقاعد وتواريخ متاحة. |
| `HousingUnit` | تعديل | يبقى كـ Accommodation مملوك لشركة؛ يزال اعتماد التحقق الإداري والعمولة، ويفصل توفره بنطاق تاريخ عن Occurrences. |
| `Booking` | إعادة بناء منطقية | يستبدل UserId ببيانات العميل، ويضاف CompanyId والمرجع والإيصال ووسيلة الدفع وحالات المراجعة اليدوية. |
| `PaymentTransaction` وPaymob/Webhooks | حذف من مسار SaaS | لا يوجد تحصيل أو تحقق آلي أو Refund في المنتج الجديد. |
| `ProviderPayout` والعمولات | حذف | المنصة لا تحصّل أو توزع أموال الحجوزات. |
| `Review` | تعديل | يصبح بدون حساب عميل، مع CompanyId وحالة Pending/Approved/Rejected تقررها الشركة. |
| Cloudinary | احتفاظ | مناسب للـ logo/cover وصور الخدمات وإيصالات التحويل. |
| Email وQR | احتفاظ مع تعديل | يؤكد الحجز بعد مراجعة الإيصال ويخدم التحقق يوم الوصول. |
| Chat، Chatbot، توصيات السائح، اهتمامات السائح | مؤجل للحذف/الاستبعاد | ليست ضمن الإصدار الأول؛ لا تحذف قبل مراجعة اعتماد الكود عليها. |
| Admin الحالي | إعادة تصميم | يتحول إلى Super Admin محدود الصلاحيات وRead-only للحجوزات. |

## 4. ترتيب التنفيذ المعتمد للمراجعة

1. **Foundation audit**: تثبيت هذه الخريطة وتحديد سياسة قاعدة البيانات القديمة.
2. **Company + identity**: كيان Company، حساب الشركة، Super Admin، وحالات الشركة.
3. **Tenant isolation**: `CompanyId`، سياق الشركة، فلاتر الاستعلام، واختبارات منع التسريب.
4. **Company onboarding**: البيانات، theme، slug، ووسائل الدفع اليدوية.
5. **Packages**: الباقات وOccurrences والمقاعد.
6. **Accommodations**: الإقامات وتوفر نطاق التواريخ.
7. **Manual booking flow**: الحجز، الإيصال، المراجعة، العربون، وتحرير السعة.
8. **QR, email, tracking**: التأكيد، QR، وتتبع الحجز العام.
9. **Reviews**: إدخال عام وموافقة الشركة.
10. **Company dashboard APIs**: الإحصاءات وإدارة كل ما سبق.
11. **Super Admin APIs**: شركات، renewals يدوية، ومراقبة الحجوزات للقراءة فقط.
12. **Angular frontend**: Dashboard الشركة، Super Admin، والموقع العام لكل Company.
13. **Hardening**: الاختبارات، التفويض، migrations، التوثيق والتشغيل المحلي.

## 5. قرارات يجب اعتمادها قبل بدء المرحلة 1

1. **سياسة قاعدة البيانات:** هل نبدأ schema/data نظيفة للمنتج الجديد، أم توجد بيانات
   تطويرية من Fayora يجب ترحيلها؟ **القرار المعتمد: قاعدة بيانات محلية نظيفة؛ لا توجد
   بيانات من Fayora القديم للترحيل أو الاحتفاظ.** ستُنشأ migrations جديدة لاحقاً، من دون
   حذف أي شيء في هذه المرحلة.
2. **اسم الدور للشركة:** الافتراضي المقترح `Company`، و`SuperAdmin` لمالك المنصة.
3. **مهلة الحجز المعلق:** المدة التي يحتفظ خلالها الحجز Pending بالمقاعد قبل أن يلغى
   تلقائياً إن لم يرفع العميل إيصالاً. لم تُحدد بعد.
4. **العربون:** هل هو متاح لكل شركة/كل خدمة بشكل افتراضي أم خيار تضبطه الشركة لكل باقة
   أو إقامة؟ لم يُحسم بعد.
5. **OAuth:** يبقى Google/Facebook للشركات فقط إن كانت المفاتيح والتكاملات الحالية قابلة
   للاستخدام؛ وإلا نبدأ بالبريد وكلمة المرور ثم نضيفهما لاحقاً.

## 6. بوابة المراجعة الحالية

لا ننتقل إلى إنشاء كيان `Company` أو أي migration قبل اعتماد سجل التحويل وقرارات
القسم 5. أول تاسك برمجي بعد الاعتماد هو: **تصميم Company والـ enums والعلاقات فقط**؛
ولا يشمل بعد التعديل في الحجز أو الباقات أو حذف Paymob.

## 7. القرارات المعتمدة أثناء التنفيذ

| القرار | الحالة | الملاحظة |
| --- | --- | --- |
| سياسة البيانات | معتمد | قاعدة بيانات محلية نظيفة؛ لا ترحيل لبيانات Fayora القديمة. |
| ملكية حساب الشركة | معتمد للإصدار الأول | لكل شركة حساب Dashboard واحد هو المالك. العلاقة `Company.OwnerUserId` فريدة ومقيدة بمفتاح خارجي إلى `User`. يُضاف نموذج أعضاء فريق لاحقاً عند الحاجة. |
| تسجيل الشركة بالبريد | معتمد | endpoint منفصل `POST /api/company-auth/register/email` ينشئ User بدور `Company` وCompany بحالة Trial ويرسل كود تحقق. لا يستخدم endpoint تسجيل Fayora القديم. |
| تسجيل Google للشركة | معتمد | endpoint منفصل `POST /api/company-auth/login/google`. أول استخدام يحتاج اسم الشركة ورقم التواصل؛ الاستخدام اللاحق يدخل مباشرة. Facebook غير مدعوم لمسارات FayoraTravel الجديدة. |
| Onboarding: بيانات الشركة وواتساب | منفذ | `GET/PUT /api/company/profile` مقصوران على دور Company ويعتمدان على هوية JWT، لا على CompanyId وارد من العميل. طلب التعديل يحمل قائمة WhatsApp كاملة؛ لذلك الإضافة والتعديل والحذف تحدث ضمن نفس حفظ بيانات الشركة. |
| Onboarding: Slug والثيم والدفع | منفذ | endpoints مستقلة للـ slug (وفحص توفره) والثيم ووسائل الدفع، مع endpoint مستقل لإتمام الإعداد بعد تحقق كل الشروط. |
| دخول الشركة بالبريد | منفذ | `POST /api/company-auth/login/email` يقبل دور Company فقط ويعيد حالة onboarding وJWT. |
| قاعدة البيانات المحلية | معتمد | اسم قاعدة FayoraTravel المحلية هو `FayoraTravelDb`، منفصل عن قاعدة Fayora القديمة ولا ترحّل إليه أي بيانات. |
